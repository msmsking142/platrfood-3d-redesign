# Calls and live location

- In-app WebRTC calls via `components/CallProvider` (in `_globalContextProviders`; exposes `useCall()` `{startCall, state, support}`) and `components/OrderCallButton` (shows disabled reasons + device-support fallback). Matrix enforced in `helpers/callStartParticipants`: customer↔rider and rider↔restaurant always during active delivery (rider assigned, statuses `accepted`–`picked_up`); customer→restaurant during `placed`–`picked_up`; restaurant→customer only if `users.allow_restaurant_calls` (toggle "Allow calls from restaurants" on `/account`). Rate limit 6 starts/10 min per caller. `calls.callee_role` CHECK allows rider/customer/restaurant. `signal_POST` ends call (409) if order no longer active; `helpers/endOrderCalls` (called from `notifyZipto`) ends calls on delivered/cancelled/rejected. In `signal_POST` joined queries must use `calls.id` (ambiguous id bug happened once). Names: restaurant sees "Customer"; rider sees customer first name. No phone numbers anywhere; Google STUN only, no TURN; callee must have app open. Privacy policy describes call data (call logs, no audio recording, P2P IP visibility).
- Phone numbers remain private: `restaurant/dashboard_GET` blanks `deliveryPhone` and `riderPhone`; hides `customerName` (shown as "Customer"), `recipientName`, `deliveryAddress`, `deliveryLat/Lng`, and `upiReference`; and redacts phones/emails in notes, rating comments, and complaint descriptions via `helpers/redactContactInfo`. `rider/dashboard_GET` blanks `deliveryPhone` and `restaurantPhone` for all orders and hides `customerName`, `recipientName`, and notes for not-yet-accepted `available` orders. Customer `orders_GET` blanks `riderPhone` and `restaurantPhone`.
- Customer call opt-in is `users.allow_restaurant_calls` (default `false`); its toggle is available on `/account` through `preferences_POST`.
- While a rider is online with an active order, `helpers/useRiderLocationSharing` sends location through `rider/location_POST`, continuing through `picked_up`. This updates `riders.last_lat/lng` and publishes to `channels.restaurantLive(restaurantId)` before pickup and `channels.orderLive(orderId)` throughout the active order. `token_POST` grants customers access to `orderlive` for their own active orders; the token must be refreshed after an order becomes active (TTL 1h).
- Customer tracking uses `components/CustomerOrderTracker`, `helpers/useCustomerRiderLocation`, and `helpers/useCustomerOrderAlerts`. `components/RiderLiveMap` (Leaflet + OSM) supports a destination pin; its outlet pin uses `restaurants.lat/lng`, set through restaurant action `set_location` (UI: `components/LocationPinPicker` in MerchantOutlet + "Set pin now" dialog in MerchantOrders via MerchantPinEditor).
- Checkout requires a delivery pin (place_order schema: deliveryLat/Lng required) via LocationPinPicker. `orderFor: self|other`; other → `orders.recipient_name` + receiver phone/address, not saved to address book.
- Rider active deliveries: RiderLiveMap + `helpers/mapNavigation.directionsUrl` (Google Maps turn-by-turn) → restaurant before pickup, customer after pickup.
